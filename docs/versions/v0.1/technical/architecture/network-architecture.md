# 联网与技术架构

> 依赖：[设计总纲](../../product/overview/design-overview.md)（§8）、[核心规则](../../product/rules/core-rules.md)、[卡牌规范与数据](../../product/content/card-system.md)（含「英雄卡」小节）
> 状态：方案未实施
> 注意：**服务端技术栈尚未确定；客户端已确定为 Godot 4 + GDScript**，见[客户端技术基线](client-stack.md)。本文只锁定与实现无关的架构约束与协议形状；服务端语言、框架、部署形态留待开发启动前决定。

本文描述服务端权威、确定性随机、协议、重连与反作弊约束；不描述具体技术选型与实现。归属版本技术基线。

## 1. 架构总览

```
┌─────────────────────── 客户端 ───────────────────────┐
│  表现层：渲染 / 动画 / 输入 / 音频                     │
│  不加载、不执行规则引擎                                 │
└───────────────┬──────────────────────────────────────┘
                │  WebSocket（意图上行、事件下行）
┌───────────────▼──────────────────────────────────────┐
│  房间服务：会话、阶段计时、广播、掉线管理             │
│  ┌────────────────────────────────────────────────┐  │
│  │  规则引擎（唯一运行位置，仅部署在服务端）        │  │
│  │  reduce(state, intent, rng) → {state, events}   │  │
│  └────────────────────────────────────────────────┘  │
└───────────────┬──────────────────────────────────────┘
                │
    ┌───────────┴───────────┐
    │                       │
┌───▼────┐            ┌─────▼─────┐
│ 匹配服务 │            │ 持久化/遥测 │
└────────┘            └───────────┘
```

### 1.1 硬约束

1. **规则引擎不依赖网络、UI、系统时间与全局随机**：输入只有 `state`、`intent`、`rng`，输出只有新 `state` 与 `events`；
2. **规则只在服务端运行**：客户端不加载、不执行规则引擎，不做本地预演；客户端的一切状态变化都来自服务端事件；
3. **单份实现**：规则引擎只部署在服务端，禁止在客户端内嵌副本或另写一套规则；客户端只使用服务端下发的展示数据；
4. **可回放**：给定种子 + 意图序列，必须能逐事件重放出完全相同的结果；
5. **两端同一套客户端**：桌面端与移动端共用同一份 Godot 4 客户端工程与协议，必须同时满足横屏与竖屏布局。

## 2. 分层与依赖规则

### 2.1 规则引擎层

- 只包含：状态定义、意图校验、效果结算、战斗模拟、数据表加载；
- 只部署在服务端：客户端不引入该模块，也不保留任何规则分支；
- 不允许：读取时钟、读取环境变量、发起网络请求、写日志以外的副作用；
- 随机数通过参数注入，禁止直接调用全局随机函数。

### 2.2 房间服务层

- 负责：房间生命周期、玩家会话、阶段计时、意图排序、广播、断线重连；
- 不负责：任何游戏规则判断；它只调用规则引擎并把结果广播出去；
- 每个房间单线程串行处理意图（或用等价的消息队列串行化），保证顺序确定。

### 2.3 表现层

- 只消费服务端事件；不执行规则、不做本地预演，也不在服务端确认前改变游戏状态；
- 即时反馈只限纯表现层（按下态、点击动效、音效），不推断任何规则结果；
- 可用性提示只能来自服务端下发的字段；客户端不自行推导「是否买得起」「能否三连」等规则结论，最终以服务端接受或拒绝为准；
- 动画时长不参与结算：`CombatResult` 已经是最终结果，播放速度只影响观感。

## 3. 对局服务状态机

对局状态机与 [核心规则](../../product/rules/core-rules.md) §2 一致（`Lobby` / `Recruit` / `Combat` / `Settle` / `GameOver`）。服务端额外维护：

- `phaseDeadline`：本阶段截止时间戳；
- `pendingIntents`：已接收但未结算的意图队列；
- `seq`：全局递增事件序号；
- `rngState`：当前随机数发生器的内部状态（可序列化）。

阶段推进只由房间服务触发，客户端事件为 `PhaseChanged`。

## 4. 确定性随机

### 4.1 种子

- 房间创建时生成 32 字节种子，写入房间元数据；
- 种子派生出若干独立流：`shop`、`combat`、`discover`、`matchmaking`、`effects`；各流互不影响，避免"刷新次数改变战斗结果"；
- 比赛模式下种子公开；会战模式下种子在对局结束后公开，用于回放与申诉。

### 4.2 可复现要求

- 随机调用点必须带标签（如 `shop.reroll.turn7`），同一标签在同一状态下必须产出同一结果；
- 规则引擎内不得使用哈希表遍历顺序、时间戳、浮点比较等不稳定因素；
- 所有概率用整数权重实现，避免浮点误差。

## 5. 协议约定

### 5.1 事件信封

```json
{
  "seq": 1287,
  "roomId": "r_8f2a",
  "playerId": "p_03",
  "type": "StateDelta",
  "payload": {},
  "ts": 1763100000000
}
```

- `seq` 单调递增，客户端据此检测丢包与乱序；
- `playerId` 为 `null` 表示广播给全房间；
- `type` 是唯一的路由键，未知类型必须被忽略而不是报错（向后兼容）。

### 5.2 消息清单

| 方向 | 类型 | 说明 |
| --- | --- | --- |
| C→S | `Intent` | 玩家意图，`payload` 为 [核心规则](../../product/rules/core-rules.md)的意图名与参数 |
| S→C | `StateDelta` | 状态增量（只含该玩家可见的部分） |
| S→C | `CombatResult` | 战斗最终结果：双方阵容快照、行动序列、伤害、胜负 |
| S→C | `Snapshot` | 全量状态快照，用于开局与重连 |
| C→S | `Reconnect` | 重连请求，携带 `lastSeq` |
| S→C | `PhaseChanged` | 阶段切换与截止时间 |
| S→C | `TimerWarning` | 招募阶段剩余 10 秒提醒（见 [核心规则](../../product/rules/core-rules.md) §8.1） |
| S→C | `Error` | 意图被拒绝，含返回码（见 [核心规则](../../product/rules/core-rules.md) §3） |

### 5.3 一次完整回合的序列

```
C→S  Intent{BuyMinion, slot:2}
S→C  StateDelta{seq:101, gold:1, board:[...], shop:[...]}
C→S  Intent{EndRecruit}
S→C  PhaseChanged{phase:Combat, deadline:+15000}
S→C  CombatResult{seq:102, actions:[...], damage:9, winner:p_03}
S→C  StateDelta{seq:103, hp:31, board:[...]}
S→C  PhaseChanged{phase:Recruit, turn:8, deadline:+90000}
```

### 5.4 意图的幂等性

- 每个意图带客户端生成的 `clientIntentId`；服务端对同一 id 只处理一次；
- 意图被拒绝时返回 `Error{clientIntentId, code}`，客户端据此结束该次操作的即时反馈，并以服务端状态为准；客户端没有可回滚的本地规则结果。

## 6. 快照与重连

### 6.1 快照内容

`Snapshot` 只包含该玩家可见的信息：自己的完整状态（手牌、金币、商店、时代、生命、所选英雄卡的技能）、公共信息（回合数、阶段、存活玩家、各玩家生命与阵容规模）、以及自己的 `seq` 水位。对手的手牌、金币、商店内容绝不进入快照。

### 6.2 重连算法

1. 客户端发送 `Reconnect{roomId, playerId, lastSeq}`；
2. 服务端校验会话令牌，返回 `Snapshot{seq: S}`；
3. 客户端丢弃本地状态，载入快照；
4. 服务端继续推送 `seq > S` 的增量事件；
5. 若断线超过 30 秒，服务端已启用 AI 托管，重连后玩家立即接管，托管期间产生的状态通过增量补齐。

### 6.3 掉线与托管

- 断线 30 秒进入托管；连续两个招募阶段无输入也进入托管；
- 托管不改变阵容结构，只做买牌/升时代/刷新；
- 玩家重连即解除托管，不等待回合结束。

## 7. 隐藏信息与反作弊

### 7.1 绝不下发的字段

| 字段 | 原因 |
| --- | --- |
| 对手手牌 | 直接决定信息优势 |
| 对手金币与时代升级进度 | 可推断其战术意图 |
| 对手商店内容与刷新次数 | 可推断其经济状态 |
| 对局种子（会战模式） | 可预测刷新与战斗结果 |
| 其他玩家的意图队列 | 可提前针对 |

### 7.2 服务端校验点

1. **意图合法性**：阶段、资源、目标存在性、次数限制；
2. **时序**：意图必须在阶段截止前到达，且 `seq` 不跳号；
3. **速率**：单玩家每秒意图数上限（建议 20），超出则丢弃并警告；
4. **重放校验**：对局结束时用种子 + 意图序列重算最终状态哈希，与实时状态比对，不一致则标记异常对局。

### 7.3 客户端篡改的检测面

- 客户端不执行规则，无法自行生成或推进游戏状态；客户端上报的任何数据都不作为真相；
- 客户端无法伪造 `seq` 之后的状态，因为每次变化都必须有服务端的 `StateDelta`；
- 对局结束的哈希校验能发现"改内存但没改服务端"的作弊者（其上报数据会与服务端重算不符）。

## 8. 匹配与房间

| 项 | 规则 |
| --- | --- |
| 账号 | 仅手机号验证码登录；账号与好友关系绑定；v0.2 起绑定天梯积分 |
| 成局方式 | 首版为创建房间、6 位房间码与好友邀请；无自动匹配与公开房间列表 |
| 匹配依据 | v0.2 引入，按天梯积分，等待 30/60/90 秒逐步放宽；好友小队按成员平均分 |
| 房间人数 | 8，全部为真人，房间满员且全部准备才可开局 |
| AI 补位 | 不设 AI 补位；人数不足时房间保持在 `Lobby` 等待 |
| 座位 | 服务端分配，写入种子 |
| 重开 | 对局结束后玩家留在房间，房主发起下一局 |
| 观战 | 首版不做，但快照结构按"可被第三方只读消费"设计 |

## 9. 容错与运维

- **房间进程崩溃**：持久化以意图日志 + 种子为准，快照每秒落盘只用于进程崩溃恢复；恢复后从最近快照 + 意图日志重建，不把快照当作长期存档；
- **时钟**：以服务端单调时钟为准，避免客户端改时间；
- **可观测性**：记录每局种子、意图序列、最终哈希、异常返回码分布；关键指标为"意图拒绝率""重连率""对局完成率"；
- **灰度**：规则变更走配置开关，按房间比例灰度，便于快速回滚。

## 10. 测试策略

### 10.1 确定性测试（最高优先级）

- 固定种子 + 固定意图序列 → 断言最终状态哈希；同一用例跑 100 次结果必须一致；
- 覆盖：商店刷新、三连、战斗、发现、断线重连后的重放。

### 10.2 属性测试

- 任意合法意图序列不产生非法状态（金币 < 0、随从数 > 7、同名三连残留等）；
- 战斗一定在 200 次行动内结束；
- 任何对局最终都能产生唯一排名。

### 10.3 协议测试

- 乱序、重复、丢失的 `StateDelta` 不能让客户端进入非法状态；
- 未知 `type` 必须被忽略；
- 重连后状态哈希必须与服务端一致。

### 10.4 平衡测试

用 AI 自动对局跑 10 万局，输出各流派胜率、平均回合数、平均伤害；这是 [数值与经济](../../product/systems/economy-and-numbers.md)自检指标的数据来源。
