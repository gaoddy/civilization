# v0.1 实现设计

> 状态：待确认
> 范围：M0 规则可跑 → M1 单房间联调 → M2 联机内测 → M3 桌面端上线
> 依据：[v0.1 版本入口](../versions/v0.1/README.md)、[版本路线与风险](../version-roadmap.md)、[服务端技术基线](../versions/v0.1/technical/architecture/server-stack.md)、[客户端技术基线](../versions/v0.1/technical/architecture/client-stack.md)、[通信协议](../versions/v0.1/technical/architecture/protocol.md)

本文只描述 v0.1 的实现架构、阶段划分与验证方式；产品规则、数值与卡牌内容不在此复制，按链接引用。

## 1. 意图与为什么

v0.1 目前只有文档、220 张卡牌数据与协议资产，没有任何可运行代码。本设计要把「文档定义的规则」变成可执行、可回放、可联机的产品：规则引擎只在服务端运行，客户端只消费服务端下发的事件与视图。

成功的定义不是"能跑起来"，而是路线图 [M0–M3 退出标准](../version-roadmap.md#2-里程碑)逐条通过。任何一条未通过，都按路线图延期，不以"上线前再补"放过。

## 2. 目标、非目标、反目标

### 2.1 目标

1. 一套确定性的 Rust 规则引擎，覆盖七时代、六流派、13 个关键词、三连、升星、招募 / 战斗 / 结算状态机的全部分支；
2. 卡牌数据从实体文档生成，引擎消费的数据与文档零漂移；
3. 可独立运行的 CLI 模拟器，支持单局重放与批量 AI 对局，产出 M0 基线报告；
4. 单房间联调：服务端 + Godot 桌面客户端完整打完一局，所有意图可用；
5. 8 人真人在线对局、房间码与好友邀请、断线重连与 AI 托管；
6. 桌面端可交付版本与对局数据后台。

### 2.2 非目标

- v0.2 内容：移动端、比赛模式、成就、自动匹配、天梯、赛季、商业化、扩展层（场景 / 陨落 / 英雄坐镇 / 大决战）；
- AI 补位与观战；
- 多语言、支付、运营后台的完整能力；
- 客户端本地规则预演或离线单机模式。

### 2.3 反目标

- 客户端执行、推断或缓存任何规则结论；
- 结算路径出现浮点比较、哈希表遍历顺序、系统时间或全局随机源；
- 服务端与客户端各有一份规则实现；
- 为单张卡写特判代码，绕过 `effects` DSL；
- 未通过 M0 验证标准就进入联网联调。

## 3. 约束

以下为既有基线，不再讨论：

- 服务端 Rust stable（edition 2024，工具链写入 `rust-toolchain.toml`），tokio、axum WebSocket、serde + serde_json、PostgreSQL + sqlx、cargo test + proptest；
- 随机数自实现 xoshiro256++，按 `shop` / `combat` / `discover` / `matchmaking` / `effects` 标签派生独立流，引擎只接受注入的随机状态；
- 规则引擎不依赖网络、UI、系统时间、I/O 与协议 crate；容器顺序用 `BTreeMap` / 有序 `Vec`；结算只用整数；`#![forbid(unsafe_code)]`；
- 协议契约唯一来源是 `protocol/schema/v1/`；客户端不做完整运行时校验；
- 客户端 Godot 4 + GDScript，只消费服务端视图与事件；
- 隐藏信息过滤发生在 `room-service`，不进入规则引擎；
- 构建、测试、生成统一走 `make`。

## 4. 方案选择

### 4.1 交付节奏

| 方案 | 说明 | 取舍 |
| --- | --- | --- |
| 一次性大爆炸 | M0–M3 同时开工，最后统一联调 | 失败面最大；规则错误会同时污染服务端、客户端与协议，无法定位 |
| **里程碑顺序（选定）** | M0 引擎 → M1 单房间 → M2 联机 → M3 桌面端，每段独立验收 | 每段有明确退出标准；M0 的错误在写 UI 之前暴露；代价是客户端较晚可见 |
| 垂直切片优先 | 先做"两人一回合 + 最小 UI"，再补规则 | 早期有画面，但引擎分支覆盖会长期不完整，违反 M0 的"未覆盖分支数为 0" |

选定里程碑顺序。M1 内部允许垂直切片：先跑通"登录 → 房间 → 一回合 → 战斗"，再补全意图与界面。

### 4.2 卡牌数据管线

| 方案 | 说明 | 取舍 |
| --- | --- | --- |
| 运行时直接解析 Markdown | 引擎或房间服务每次启动读实体文档 | 引入自写 YAML 子集解析；引擎被迫依赖文件 I/O；启动慢 |
| Rust `build.rs` 解析 | 编译期生成常量 | 解析逻辑落在 Rust，与现有 Python 校验脚本重复；改文档要重编译 |
| **Python 生成 + 提交 JSON（选定）** | `scripts/gen_card_data.py` 复用现有 front matter 解析，输出 `server/data/v0.1/*.json`；`make data-check` 比对漂移 | 与现有工具链一致；生成物可审阅；引擎保持无 I/O；代价是数据变更要重跑生成 |

生成物随源提交。引擎提供 `Catalog::from_json(&str)`，由 `sim` 或 `room-service` 读文件后注入。

### 4.3 效果执行

| 方案 | 说明 | 取舍 |
| --- | --- | --- |
| 手写每张卡逻辑 | 按卡牌 id 分支 | 220 张卡不可维护，改卡即改代码 |
| 构建期代码生成 | DSL → Rust 代码 | 生成器本身成为第二套解释器；调试与覆盖统计困难 |
| **加载期解析 + 运行期解释（选定）** | DSL 解析为类型化 AST，加载时全量校验；运行期按触发时机与结算顺序解释 | 单一实现覆盖全部卡；新增卡不改代码；代价是解释器要覆盖 15 触发 / 12 动作 |

选定解释器。加载期任何未知触发、动作、选择器或参数都直接报错，不允许"运行到才失败"。

### 4.4 工程形态

| 方案 | 说明 | 取舍 |
| --- | --- | --- |
| 单 crate + 模块 | 起步快 | M1 的协议与房间服务只能挤在同一 crate，依赖方向无法由编译期保证 |
| **Cargo workspace（选定）** | 直接建 `server/` workspace；M0 只有 `rule-engine` + `sim`，M1 加 `protocol` + `room-service` | 一开始就有 crate 边界，后续不搬迁；代价是 M0 多一层目录 |

## 5. 里程碑架构

### 5.1 M0 规则可跑

#### 目录

```
server/
  Cargo.toml                 # workspace、依赖锁定
  rust-toolchain.toml
  data/v0.1/
    cards.json               # 生成物
    skills.json              # 生成物
    tokens.json              # 生成物
  crates/
    rule-engine/             # 纯库
      src/lib.rs
      src/state.rs           # GameState / PlayerState / MinionInstance / 牌池
      src/data.rs            # Catalog、Card、Skill、Token 类型与加载期校验
      src/effects/           # DSL 解析、AST、解释器、选择器
      src/intent.rs          # 意图校验与拒绝码
      src/recruit.rs         # 商店、买/卖/刷新/冻结/升时代/打出
      src/combat.rs          # 战斗模拟、目标选择、行动循环
      src/settle.rs          # 伤害、淘汰、排名、第 20 回合收束
      src/rng.rs             # xoshiro256++ 与标签流
      src/view.rs            # 领域视图（协议无关）
      src/hash.rs            # 规范序列化与状态哈希
    sim/                     # 可执行：CLI 模拟器 + 确定性 AI
  tests/                     # 跨 crate 集成、重放与批量
scripts/gen_card_data.py
```

依赖方向：`sim → rule-engine`；`rule-engine` 不依赖 `sim`、tokio、sqlx、协议。

#### 引擎 API

```rust
Engine::new(config: GameConfig, catalog: Catalog, seed: [u8; 32]) -> GameState
Engine::apply(state: &mut GameState, intent: Intent) -> Result<Transition, Reject>
Engine::view_for(state: &GameState, seat: Seat) -> PlayerView
Engine::state_hash(state: &GameState) -> u64
```

- `apply` 是唯一的状态变更入口；它不读时间、不读环境、不写文件。
- `Transition` 包含本意图产生的 `GameEvent`（供房间服务转成动画事件）与是否推进阶段。
- `Reject` 携带核心规则 §3 的返回码；拒绝不改变状态。

#### 状态模型要点

- `GameState`：回合数、阶段、座位、玩家、共享牌池、各随机流状态、先手方、场景配置（默认关闭）、哈希所需字段；
- `PlayerState`：生命、金币、时代、在当前时代停留回合数、商店槽位与冻结位、战场、手牌、英雄卡、已用技能次数、本局累计伤害、是否托管；
- `MinionInstance`：实例 id、卡牌 id、金色标记、`growth`、`breed`、`contagion`、派生关键词、临时修饰、战斗标记（护盾、复生已用、攻击次数、禁攻）、站位；
- 牌池：按 `card_id` 计数的 `BTreeMap`；召唤、复制、出售、三连分别按核心规则 §6 扣还。

#### 结算顺序

严格按文档执行，不自行合并：

1. 招募：回合开始（繁衍 → 传染 → 其他回合开始效果）→ 玩家意图 → 三连判定 → 战吼 / 装配；
2. 战斗：`CombatStart` 被动与延迟战吼 → 行动循环（核心规则 §5.2 第 1–8 步）→ 死亡结算（亡语 → 播种 → 复生）；
3. 结算：清除临时增益 → 伤害 → 淘汰 → 排名 → 第 20 回合收束。

#### 效果解释器

- 解析 `effects` 为 `Vec<Effect>`；每个 `Effect` 含 `trigger`、`op`、`selector`、参数表；
- 选择器解析为「阵营 + 选取方式 + 筛选条件」，`single` 表示由意图或玩家选择提供目标；
- 解释器按触发时机收集效果，按"先手方 → 后手方、站位从左到右、单卡文本从上到下"排序执行；
- 光环在任何区域变化后全量重算；光环失效不致死；
- 加载期校验覆盖：触发白名单、动作白名单、参数必填/互斥/取值范围、选择器筛选键、`timesIf` / `condition` 语法、`duration`；
- 覆盖报告：按「触发 × 动作」统计技能使用数；出现零覆盖的组合不报错，但列入 `sim` 的覆盖报告，供规则用例补齐。

#### 随机与确定性

- 种子派生五个标签流；每次随机调用以标签 + 流状态为键；
- 商店抽取：整数权重选出星级 → 在符合"本局启用流派 + 牌池有剩余"的卡中均匀抽取；
- 战斗随机目标、发现、复制等全部走注入的流；
- 状态哈希：对规范编码（BTreeMap 顺序、整数、Vec 顺序）计算，不含内存地址与时间。

#### 模拟器与 AI

- CLI 子命令：`sim play --seed`（单局）、`sim batch --games 1000 --seed`（批量）、`sim replay --log`（重放校验）、`sim report`（基线报告）；
- AI 是 `sim` 内的确定性策略，只发送合法意图，不进入规则引擎：优先买得起的最贵卡 → 填满棋盘 → 升时代 → 刷新 → `EndRecruit`；英雄技能按"可支付且未用尽"使用；
- 输出：胜负、淘汰顺序、排名、各流派胜率、平均回合数、升星时点、三连次数、单局时长（按回合数计）、状态哈希；
- 批量对局支持固定并发度与超时；任一局崩溃、死锁或未判定即非零退出。

#### DSL 审计（M0 第一步）

引擎开工前先做效果 DSL 审计，避免解释器在真实数据上"运行到才失败"：

- 新增 `scripts/audit_effects.py`，枚举 118 个技能的 `effects`，按[关键词与机制](../versions/v0.1/product/rules/keywords-and-mechanics.md) §9.4 的语法解析，输出「触发 × 动作 × 选择器 × 参数」使用矩阵与不合规项；
- 矩阵覆盖全部实际数据；文档未定义或自相矛盾的组合列为待裁决，先改文档再改代码；
- 已知需在审计阶段确认的语义：`timesIf` 与 `condition` 是替换还是叠加、`when` 限定的是事件对象还是目标、`Discover` 的 `pool` / `choose` 与"三选一"的对应、`GrantKeyword` 的 `value` 必填规则、`GainMinion` 的必填参数、`source` 参数的用途；
- 审计脚本加入 `make data-check`；审计不通过不进入引擎实现。

#### M0 覆盖口径

"未覆盖分支数为 0"按以下判定，避免把无法成立的组合也算作缺口：

- **规则用例清单**取文档显式列出的分支：核心规则 §3 的九种意图与失败码、§5 的 1–8 步、§6 的三连与发现、§7 的淘汰与排名、§8 的边界情况；关键词机制 §1–§3、§10 的判定与求值；时代与数值的升降级、概率、牌池、伤害公式；
- 每个列出的分支至少一个用例；
- 「触发 × 动作」中没有任何卡牌使用、或规则上无法成立的组合（如招募阶段 `enemy:single`）不要求用例，只进入覆盖报告。

#### M0 验证

| 项 | 命令 |
| --- | --- |
| DSL 审计 | `make data-check` |
| 数据与文档一致 | `make data-check` |
| 文档校验 | `python3 scripts/validate_docs.py` |
| 单元与规则分支 | `make test` |

### 5.2 M1 单房间联调

- `crates/protocol`：用 `typify` 从 `protocol/schema/v1/` 生成 Rust 类型，生成物提交；`make protocol-rs` / `make protocol-rs-check`；
- `crates/room-service`：axum WebSocket、认证会话、房间生命周期、阶段计时、每房间单 task 串行意图、`clientIntentId` 去重、按玩家过滤视图、逐玩家发送、`Snapshot` 与重连；
- 意图映射：`protocol::Intent` → `rule_engine::Intent`；拒绝码 → `ErrorMessage`；
- 视图映射：`rule_engine::PlayerView` → `protocol::PlayerView`；`affordances` 由引擎计算，客户端只读；
- `client/`：Godot 4 工程，场景为登录、大厅、房间、对局、结算；WebSocket 客户端、单一状态存储、事件动画队列、战斗只播放 `CombatResult`；
- 开发机器人：`sim` 增加仅开发使用的 `bot --connect` 模式，通过 WebSocket 以普通客户端身份加入房间；不复制任何规则，服务端仍为唯一结算方。M1 端到端验收用 1 个 Godot 客户端 + 7 个开发机器人；
- 会话与房间状态在 M1 全部驻留内存；PostgreSQL、账号与好友从 M2 开始；
- `Ready`、`SelectHeroCard` 属于大厅消息，不是核心规则 §3 的九种对局意图：由 `room-service` 管理大厅状态，开局时把所选英雄写入引擎的初始状态；M1 的"九种意图全部可用"指九种对局意图。
- 协议若需新增字段，先改 schema + 样例 + 生成物，再改两端；不得手写与 schema 不一致的类型。

M1 退出：本地服务端 + 客户端 + 开发机器人完整打完一局；九种意图全部可用；招募 / 战斗 / 结算界面可读；规则全部由服务端结算。

### 5.3 M2 联机内测

- PostgreSQL 迁移：账号、令牌、好友关系、好友申请、房间元数据、对局、玩家对局记录、意图日志、遥测事件；
- 手机号验证码登录：`SmsSender` 抽象；开发环境用固定验证码并写日志，生产实现按部署配置接入；令牌只存哈希，30 天有效；
- 好友：申请、确认、列表、邀请加入房间；房间码分享；
- 重连与托管：断线 30 秒托管、连续两个招募阶段无输入托管、重连返回全量快照；
- 持久化与恢复：意图日志 + 种子为准，快照每秒落盘只用于进程崩溃恢复；对局结束重算状态哈希并比对；
- 部署：单二进制 + Dockerfile，初期单实例。

M2 退出：8 人真人对局完成率 ≥ 90%；断线重连后状态一致。

### 5.4 M3 桌面端上线

- 桌面端导出与发布流程；目标操作系统在进入 M3 时确认；
- 对局数据后台：对局统计、赛后数据回顾；形态（管理页面 / HTTP API / 导出）在进入 M3 时确认，并同步修订协议文档"HTTP 只保留 `/healthz`"的约束；
- 可观测性：每局种子、意图序列、最终哈希、返回码分布、重连率、完成率；
- 桌面端完整对局验收；崩溃率、意图拒绝率、单局时长作为观察项记录，不阻断上线。

M3 退出：桌面端可完成完整对局；所有意图可用；观察项已记录；数据后台可查询对局统计与赛后回顾。

## 6. 数据契约

### 6.1 卡牌数据生成物

`server/data/v0.1/cards.json` 每项字段与卡牌实体文档的 front matter 一一对应：`id`、`card_type`、`name`、`tribe`、`subtype`、`level`、`era`、`attack`、`health`、`skills`、`is_scholar`、`is_hero`、`cost`、`match_text`。缺省值在生成时显式写出（如 `is_hero: false`），避免引擎侧隐式默认。

`skills.json`：`id`、`name`、`keyword`、`text`、`effects`（原始 DSL 字符串）、`cost`、`uses_per_turn`、`match_text`。

`tokens.json`：`id`、`name`、`attack`、`health`、`keywords`。

生成器与 `validate_docs.py` 共用 front matter 解析语义；生成顺序按 `id` 排序，保证逐字节确定。`make data-check` 重新生成到临时文件并比对。

### 6.2 配置

以下常量进入 `server/data/v0.1/config.json`（或 `rule-engine` 内置常量并在生成时校验）：时代顺序与费用、商店概率矩阵、星级牌池份数、金币曲线、伤害上下限、回合上限、初始生命、手牌与战场上限。产品文档是唯一来源，配置项在生成时从文档口径抄录并由测试断言与文档一致。

### 6.3 协议

- M0 不改协议；
- M1 由 schema 生成 Rust 类型，`make protocol-check` 增加 Rust 生成物漂移检测；
- 协议演进只走"同一 `v` 内新增可选字段 / 新增类型"，上线后改名与改语义走 `v: 2`。

## 7. 验证策略

| 里程碑 | 必须通过 |
| --- | --- |
| M0 | 数据零漂移、文档校验、全部规则分支用例、100 次重放哈希一致、1000 局无崩溃/死锁/未判定、基线报告生成 |
| M1 | `make protocol-check`、cargo test、单房间端到端完整对局、九种意图覆盖、客户端只读断言 |
| M2 | 8 人机器人集成测试、重连逐字段一致、数据库迁移重放、完成率 ≥ 90% |
| M3 | 桌面端完整对局验收、数据后台查询、观察项记录 |

测试只覆盖本次改动涉及的功能；功能改动时测试同批更新，全量与无关回归不属于单个任务的验收项。但 M0 的批量与确定性验证是里程碑闸门，不按任务缩范围。

## 8. 风险与缓解

| 风险 | 信号 | 缓解 |
| --- | --- | --- |
| 规则歧义导致返工 | 实现中发现总纲歧义 > 5 处 | 立即登记 `open-questions.md`；M0 内先冻结口径再继续，超过 5 处暂停新内容 |
| DSL 语义未覆盖 | 出现文档未定义的选择器组合或触发时序 | 加载期失败 + 覆盖报告；先补文档再补解释器，不在代码里发明语义 |
| 角色被动与 Aura 交互复杂 | 战斗结果与推演不符 | 用固定种子的最小用例逐条固化文档顺序；不靠人工对局判断 |
| 1000 局性能 | 批量运行超时 | 引擎无 I/O、纯整数；必要时提高并发度与单局上限，不降低验证局数 |
| Godot 本机缺失 | 无法运行客户端 | M1 开始前安装 Godot 4 并锁定小版本；安装前只做服务端侧 |
| 客户端 UI 未定义 | 页面与交互无法开工 | M1 前按 UI 设计流程补界面方案；先做可读的最小界面，不扩交互 |
| 移动端与扩展层被提前卷入 | 任务范围蔓延 | 以第 2.2 节非目标为准，出现即拆到 v0.2 |

## 11. 实现口径裁决

以下为文档未明确、但实现必须唯一的点；先按此执行，确认后回写对应基线文档。

| 项目 | 裁决 | 理由 |
| --- | --- | --- |
| 成局方式 | 只做房间码与好友邀请，不做自动匹配、公开房间列表与 AI 补位；自动匹配属于 v0.2 | v0.1 版本基线与路线图已定 |
| 房间内战斗对手配对 | 每回合由 `rule-engine` 用 `matchmaking` 流产生配对；人数 ≥ 3 时优先排除上一场对手，仍有多解时按随机流决定；奇数人数按核心规则 §8.3 打镜像幽灵。这是房间内"谁打谁"，不是成局匹配 | 文档只写了"优先排除上一场对手"，没有算法；放进引擎才能保证重放一致 |
| 镜像幽灵 | 取该玩家上一场阵容快照，只保留永久属性；无快照用当前阵容；失败不扣血、不触发连胜/连败 | 核心规则 §8.3 已定义，补"由引擎在配对阶段生成" |
| 协议与产品文档冲突 | 以 `protocol/schema/v1/` 与 `protocol.md` 为准；开发期允许同一 `v` 内改字段，但必须同批更新样例、生成物与测试 | 协议文档 §8、§9 已定 |
| 断线托管的操作边界 | 只允许买牌（空位/手牌）、升时代、刷新、结束招募；不卖牌、不调整站位 | 核心规则 §8.1 "不改变阵容结构" |
| M2 遥测 | 只记录对局行、玩家对局行、意图日志与返回码分布；赛后回顾所需字段在 M3 确认后台形态后扩展 | M3 才定后台形态，避免提前定型 |
| 数值基线越界 | 登记 `open-questions.md`，不阻断 M0 | 路线图 M0 验证标准已定 |
| 文档歧义判定 | 同一合法操作序列在两种读法下产生不同结果即为歧义；登记最小复现用例；超过 5 处按路线图暂停新内容 | 路线图的止损线需要可操作定义 |

M0 开工后若出现上表未覆盖的歧义，先登记、给出默认读法并继续；影响面跨核规则（状态机、结算顺序、随机源）时暂停并向用户确认，不静默选择。
