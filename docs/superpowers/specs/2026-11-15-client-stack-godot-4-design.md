# 客户端技术选型 Godot 4 设计

> 状态：已确认

## 意图与原因

用户决定 v0.1 客户端使用 Godot 4，脚本语言使用 GDScript。此前所有文档统一标注「技术栈尚未确定」，客户端侧的兜底默认方案是 Web（TypeScript + Canvas/DOM）。这条决定替换客户端一半的默认方案，让后续技术基线、待确认事项与版本路线保持一致。

本轮只出文档，不搭建客户端工程，也不改变服务端技术栈。

## 目标

- 在 v0.1 技术基线中新增客户端技术基线，记录引擎、语言、目标平台、协议对接与边界。
- 改写现有文档中「技术栈未定」「渲染技术待选型」「客户端 Web」等表述。
- 把仍未确定的客户端事项收敛到 `open-questions.md`。

## 非目标

- 不创建 Godot 工程、不引入依赖、不改动任何代码。
- 不决定服务端技术栈。
- 不调整 22–31 人周的排期估算。
- 不设计具体页面布局、断点或控件结构。

## 约束

- 客户端不加载、不执行规则引擎，不做本地预演；状态变化只来自服务端事件。
- 客户端不自行推导规则结论（是否买得起、能否三连等），以服务端接受或拒绝为准。
- 桌面端与移动端共用同一份客户端工程与协议，同时满足横屏与竖屏布局。
- 协议为 WebSocket + JSON，事件信封与消息清单沿用 `network-architecture.md`。

## 设计

### 新增 `docs/current/technical/architecture/client-stack.md`

标注「方案未实施」，内容固定为：

1. 选型表：引擎 Godot 4（小版本在工程初始化时锁定）、语言 GDScript（不使用 C#）、目标平台桌面端 + 移动端同一份工程、网络 WebSocket + JSON。
2. 边界：不加载规则引擎、不做本地预演、不推导规则结论、战斗只播放 `CombatResult`，均指向 `network-architecture.md` 对应硬约束。
3. 横竖屏：同一场景树用 Control 节点与容器适配，不维护两套界面；具体断点与布局留给 UI 设计。
4. 未确定事项：链接 `open-questions.md`。

### 就地改写

- `design-overview.md` §8 引导句：客户端已确定为 Godot 4 + GDScript，服务端待定；第 7 条去掉「渲染技术待选型」；§9 删除「客户端渲染方式（DOM / Canvas / WebGL）」。
- `network-architecture.md` 头部注记与硬约束第 5 条：客户端定为 Godot 4 + GDScript，服务端仍未定。
- `technical/README.md`：补客户端选型结论与链接。
- `technical/architecture/README.md`：索引新增文档，并修正「不描述技术选型」的范围说明。
- `open-questions.md`：技术栈条目改为「服务端技术栈未定」；新增客户端工程目录、构建导出流程与测试框架的待确认项。
- `version-roadmap.md`：风险行与「技术选型」决策点改为服务端选型，兜底方案去掉客户端 Web。
- `versions/v0.1/README.md`：客户端行补引擎与语言。
