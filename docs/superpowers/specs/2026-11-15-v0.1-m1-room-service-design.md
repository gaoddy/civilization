# v0.1 M1 单房间联调实现设计

> 上游：[v0.1 实现设计](2026-11-15-v0.1-implementation-design.md) §5.2、[通信协议设计](2026-11-15-protocol-design.md)。
> 状态：待批准。

## 1. 意图与为什么

M0 已交付纯规则引擎与模拟器，规则由服务端结算但还没有网络层。M1 的目标是让真实客户端通过协议完整打完 8 人一局：协议 Rust 类型、WebSocket 房间服务、逐玩家视图、开发机器人，以及一个最小可读的 Godot 客户端。M1 不引入数据库与账号体系（M2 起）。

## 2. 目标、非目标、反目标

**目标**
1. 协议 schema 的 4 处 M0 遗留缺口先补齐，Rust 类型由 schema 生成、生成物提交、漂移检测进 `make`。
2. `room-service` 用 axum 提供 WebSocket：认证会话（M1 内存版）、房间码建房/加入、准备与选英雄、阶段计时、每房间串行意图、`clientIntentId` 去重、按玩家过滤视图、全量快照与重连。
3. 引擎新增 `PlayerView` 构造与 `affordances` 计算；客户端不推导规则。
4. `sim bot --connect` 以普通客户端身份走真实协议；M1 端到端验收用 8 个机器人（M1a）与 1 个客户端 + 7 个机器人（M1b）。
5. Godot 4 最小可读界面：登录、大厅、房间、对局、结算五场景，不做美术与动效。

**非目标**
- PostgreSQL、手机号短信、好友、托管、对局持久化（M2）；
- 自动匹配、公开房间列表、观战（v0.1 不做，v0.2 起）；
- 桌面端导出与发布（M3）。

**反目标**
- 客户端本地结算规则或自行推导可操作状态；
- 手写与 schema 不一致的 Rust 类型；
- 为 UI 方便在协议里暴露对手手牌、金币、商店或对局种子。

## 3. 约束

- 协议唯一来源是 `protocol/schema/v1/`；演进只允许在同一 `v` 内新增可选字段/类型。
- 规则结算只在 `rule-engine`；`room-service` 不复制规则，只做会话、时序与视图映射。
- 引擎保持纯库：视图构造是纯函数，不读时钟；`phaseDeadline` 由 `room-service` 注入。
- 每房间单 task 串行处理意图，保证同一房间内顺序确定；跨房间可并发。
- 构建、测试、生成统一走 `make`；新增 `protocol-rs`、`protocol-rs-check`、`m1-check`。

## 4. 方案选择

**选定：拆 M1a（服务端侧）与 M1b（客户端侧），两段各自可验收。**
- M1a：协议 + 房间服务 + 引擎视图 + 机器人。用 8 个机器人经真实 WebSocket 打完一局，覆盖十种意图、拒绝码、快照与重连。不依赖 Godot，可在 CI 跑。
- M1b：Godot 最小五场景，用 1 个客户端 + 7 个机器人做人工端到端验收。
- 理由：Godot 本机刚安装、界面方案未细化；把服务端契约先钉死，客户端只消费协议，返工面最小。

**被否方案**
- 一次性做完服务端与客户端：客户端问题会与服务端契约问题混在一起，无法逐段验收。
- 先做客户端再补服务端：违反「服务端权威、规则唯一来源」，客户端将是无法验证的假实现。

## 5. 设计

### 5.0 实现前必须先修的 M0 缺陷

产品规则「[卡牌规范与数据](../versions/v0.1/product/content/card-system.md) §2.1」明确：**多人局允许重复选择同一张英雄卡，英雄身份互不影响**。M0 的 `Engine::start_game` 却要求 8 个座位的英雄卡互异，与产品规则冲突。

M1 第一步修正：`start_game` 只校验每个座位选的卡在目录中存在且 `is_hero: true`，不再要求互异；同步改测试与大堂状态机（准备条件 = 8 人都已选英雄且已准备）。这是产品规则的回归修复，不是新规则。

### 5.1 协议补齐（先改 schema + 样例 + 生成物，再改两端）

1. **意图目标参数**：`BuyMinion`、`PlayCard` 增加可选 `targetMinionId`；引擎映射为 `target: Option<InstanceId>`。
2. **发现/进化选择消息**：新增对局意图 `ChooseDiscover { choice }`，同时覆盖引擎的 `PendingChoice::Discover` 与 `PendingChoice::Evolve`（引擎按座位 FIFO 消费，`choice` 对发现是候选下标、对进化是选项下标），同步核心规则 §3、schema、样例与生成物；越界返回 `INVALID_CHOICE`。协议意图因此是**十种**：核心规则 §3 的九种 + `ChooseDiscover`；文档与验收口径统一按十种。
3. **视图补字段**：
   - `PlayerView.self.pendingChoices`：待选列表，每项 `{ kind: "discover"|"evolve", candidates: [cardId] | options: [evolveOption] }`；无待选为空数组。客户端不自行推导待选。
   - `PlayerView.opponentPlayerId`：本回合对手座位对应的玩家 id；镜像幽灵时（无真实对手）为 `null`。
   - `players[].placement`：已淘汰玩家的名次，未淘汰为 `null`。
   - `players[].managed`：托管标记，M1 恒 `false`，M2 起可能为 `true`。
   - 对手阵容、手牌、金币、商店、刷新次数、种子仍不进入视图。
4. **认证补字段**：`AuthRequest` 增加可选 `displayName`；缺省由服务端生成「玩家N」。`playerId` 由服务端生成不透明串，M1 只在内存保存。
5. **生成位置**：统一为仓库根 `protocol/generated/protocol.rs`，`crates/protocol` 依赖该生成文件（`include!`），`make protocol-rs` 生成、`protocol-rs-check` 做漂移检测。回写 `server-stack.md`。

**不做**：M1 不以「防止客户端从商店空槽推断种子」为目标；种子在 `GameOver` 已公开，视图不展示种子顺序即可，不额外编码商店槽位。

### 5.2 `crates/protocol`

- `typify` 从 `protocol/schema/v1/*.schema.json` 生成全部类型；crate 只重导出并加信封枚举，不写业务逻辑。
- 生成脚本进 `scripts/gen_protocol_rust.py`（或直接 `cargo run -p protocol-gen`），输出稳定排序、逐字节确定；`--check` 重新生成到临时文件比对。
- 单测：样例 JSON 逐条反序列化；信封的 `type` 判别与 `payload` 类型一致；未知 `type` 失败。

### 5.3 `crates/room-service`

- axum 1 个 WebSocket 路由 `/ws`，JSON 信封；会话表 `playerId → (tokenHash, connection)` 驻留内存。
- 房间状态机：`Lobby`（加入/离开/准备/选英雄）→ 8 人准备且英雄互异 → `GameStarted` → 引擎逐回合驱动；阶段计时用注入的 `Clock` trait（生产实现取系统时钟，测试用假时钟）。
- 每房间一个 `tokio::task` 串行消费意图；意图先按 `clientIntentId` 查去重表（保留到房间销毁），再映射到引擎、执行、生成逐玩家视图、广播 `StateUpdate`；被拒绝回 `Error`。
- 事件过滤与序号：引擎事件带 `seat`，由 `room-service` 过滤——每个座位只收到与自己相关的事件（该座位自己的操作、作用于自己的伤害/淘汰、全房间可见的 `TripleFormed`/`PlayerEliminated` 等）；隐藏信息事件（对手购买、刷新、升级、商店内容）不发。`seq` 按**每个座位各自的可见事件流**递增，重连时用该座位的 `lastSeq` 判断是否需要 `Snapshot`。
- 待选期间计时：招募 90 秒计时不因待选暂停；超时由服务端自动 `EndRecruit`，未消费的待选按引擎现有语义保留。M1 不新增拒绝规则。
- 视图：`room-service` 取引擎的 `PlayerView`（公开部分）+ 座位自己的完整状态 + `affordances` + `pendingChoices`；`phaseDeadline` 由房间计时器给出。
- `CombatResult`：每场战斗结算后，为参与该对战的每个真实座位各发一份逐座位战斗回放（只含该座位可见的双方阵容与行动序列）；镜像幽灵战只发给该座位并标注 `mirror: true`；与第三方无关的 bot 对 bot 战不发。引擎为此新增逐座位战斗报告 API（由 `resolve_combat` 的结算结果派生，不重跑战斗）。
- `Snapshot` 与 `Reconnect`：返回当前序号与全量视图；重连不重放历史，靠 `lastSeq` 判断是否补齐。
- 断线：M1 只保留连接 30 秒（不做托管）；超时由房主或计时推进，M2 再接托管。

### 5.4 引擎视图映射

- `rule-engine` 新增 `view.rs`（纯函数）：`pub fn view(state, seat, catalog) -> PlayerView`，含 `affordances` 与 `pendingChoices`；不读时钟。
- `affordances` 复用引擎现有的意图校验逻辑（`recruit::apply` 的只读预检），避免两套规则。为此把各意图的校验抽成 `check_*`，执行路径复用同一 `check_*`。
- 视图只包含协议 schema 列出的字段；对手阵容、手牌、金币、商店、种子一律不出现。

### 5.5 `sim bot`

- `sim bot --connect ws://... --room CODE --name N --seed S`：AuthRequest（开发环境固定验证码）→ JoinRoom → Ready → SelectHeroCard → 循环用 AI 决策发送 `Intent` → 处理 `StateUpdate`/`CombatResult`/`GameOver`。
- 只使用协议 crate；不链接引擎内部 API 做结算，仅复用 `ai` 的决策函数（输入来自视图）。为避免复制规则，AI 决策改为同时接受 `PlayerView`；M0 的单机模式保留。

### 5.6 Godot 客户端（M1b，最小可读）

- `client/` Godot 4 工程；五个场景：登录（手机号+固定验证码）、大厅（建房/加入/房间码）、房间（成员、准备、选英雄）、对局（商店/手牌/棋盘/玩家列表/计时/结束招募/待选弹层）、结算（排名、淘汰顺序）。
- 单一 `GameStore` 保存最新 `PlayerView`，所有 UI 只读；`StateUpdate` 整包替换，事件只进动画队列。
- 网络层用 `WebSocketPeer`，自动重连；协议字段常量由 `scripts/gen_protocol_gdscript.py` 生成。
- 英雄技能与卡牌名称等静态信息：由产品文档生成只读的 `cards`/`skills` 表随客户端打包，客户端只用于展示（技能名、费用、卡名），不做任何规则计算；对手状态仍只来自视图。
- 对局界面只提供协议允许的操作；按钮可用性直接取 `affordances`，待选弹层直接取 `pendingChoices`。

### 5.7 验收

- M1a：`make m1-check` = `protocol-rs-check` + `protocol-check` + `cargo test --workspace` + 8 机器人完整对局（真实 WebSocket，退出码 0，事件与排名可判定）；**十种意图**各至少一次成功用例（含 `ChooseDiscover` 消费发现与进化）；重连后视图与序号一致；英雄卡重复选择可正常开局。
- M1b：1 个 Godot 客户端 + 7 个机器人打完一局；五场景可读；客户端无本地结算（代码审查 + 只读断言：客户端不链接 `rule-engine`）。

## 6. 风险

| 风险 | 缓解 |
| --- | --- |
| 协议缺口补齐引发 M0 引擎改动 | 只加可选字段与一个意图，引擎侧改动限定在 `intent.rs` 与视图映射 |
| typify 生成物不稳定 | 固定 typify 版本；生成排序稳定；`--check` 进 CI |
| 房间并发与计时导致不确定 | 每房间单 task；时间只由 `Clock` 注入；测试用假时钟 |
| Godot 场景与协议字段漂移 | GDScript 常量由 schema 生成，样例测试兜底 |
| UI 范围蔓延 | 五场景最小可读，不做美术/动效；超出即拆到 v0.2 |
